# API contract, client identity and force-update

How the Lubist customer app stays in step with the backend, identifies itself on
every request, and gets blocked / redirected when it has to be.
The Lubist Partner app (`lubist_vendor_application`) has the same setup with its
own identity; see its `docs/API_CONTRACT.md`.

## 1. Where the API types come from

The backend exports its OpenAPI contract to a committed file:

```
backend/openapi/openapi.json      # regenerated by: python scripts/export_openapi.py
```

This app generates TypeScript from it:

```
src/services/api/generated/schema.d.ts   # GENERATED - never edit by hand
src/services/api/types.ts                # thin helpers over it
```

`types.ts` exports:

| Helper | Meaning |
|--------|---------|
| `Schema<'PublicSalonResponse'>` | a named component schema |
| `ApiResponse<'/api/v1/salons/public', 'get'>` | JSON body of the 2xx response |
| `ApiRequestBody<'/api/v1/auth/login', 'post'>` | JSON request body |
| `ApiQuery<'/api/v1/vendors/bookings', 'get'>` | query-string params |
| `WithFields<T, {...}>` | replace fields of a generated type |

The hooks in `src/services/api/hooks/use*API.ts` derive their request/response
types from these. Hand-written shapes remain **only** where the backend declares
a field as a free-form `object` (e.g. `services: object[]` on
`SalonServicesResponse`, `favorites: object[]`, product rows); those are
overlaid with `WithFields` and commented as such. If the backend gives such a
field a real response model, delete the overlay.

### Workflow after a backend change

```bash
# in backend/  (venv active)
python scripts/export_openapi.py          # refresh openapi/openapi.json

# in this repo
npm run api:types                          # regenerate schema.d.ts
npm run typecheck                          # every drift now shows up as a TS error
```

Fix the errors (or consciously overlay them), commit `schema.d.ts` together with
the code change.

- Contract source: `$API_CONTRACT` (a path or an http(s) URL) if set, otherwise
  `../backend/openapi/openapi.json` (the backend repo checked out next to this one).
- `npm run api:check` regenerates in memory and exits 1 if the checked-in
  `schema.d.ts` differs from the contract. Use it in CI / before a release.
- Generation uses `defaultNonNullable: false`, so a field with a server default
  is optional to send (otherwise every request body would have to spell out
  every default).

## 2. Client identification headers

Every request (`services/api/client.ts`, including the token refresh call, and
`services/upload/uploadService.ts`) sends:

| Header | Value |
|--------|-------|
| `X-Client-App` | `customer-app` |
| `X-App-Version` | `expo.version` from app.json, via `expo-constants` |
| `X-App-Platform` | `ios` / `android` (`web` in the browser dev preview) |

Defined in `src/app/config/clientApp.ts`. The version comes from
`Constants.expoConfig.version` rather than `expo-application` so this ships over
OTA with no new native module. Because `runtimeVersion.policy` is `appVersion`,
an OTA bundle only ever runs on a binary with the same `version`, so this is the
native version in practice. **Bump `expo.version` for every store build** - it is
what the backend compares against `min_supported_version`.

## 3. Force update

`GET /api/v1/app-config?client_app=customer-app&platform=<ios|android>&version=<semver>`
returns `update_required`, `update_available`, `store_url`, `message`, ...

- Checked on launch (alongside session restore) and again whenever the app comes
  back to the foreground, at most once every 30 minutes
  (`src/services/appGate/appConfig.ts`).
- `update_required` -> blocking full-screen **Update required** screen with an
  **Update now** button that opens `store_url` (fallback: this app's Play listing,
  `com.lubist.mobile`). Android back is swallowed while it shows.
- `update_available` -> a dismissible banner, at most once per app session.
- **Any** API call that returns **HTTP 426** (`error_code: APP_UPDATE_REQUIRED`)
  opens the same blocking screen, using the 426 body's `store_url` if present.
  A 426 from the token-refresh call does **not** log the user out.
- If a later app-config check says the build is no longer below the minimum, the
  block is lifted.

**Fails open.** A 404 (a backend deployed before this endpoint existed), any other
error status, a timeout (8 s), a network failure or an unexpected body is treated
as "no policy" and the app carries on normally. Web / dev preview skips the check.

UI: `src/shared/components/AppGate.tsx`, mounted in `AppProviders` around the
navigation container. State: `src/services/appGate/appGateStore.ts` (a tiny
external store so the non-React API client can set it).

## 4. Partner-account redirect

Salon partner (vendor) accounts belong in the **Lubist Partner** app.

- Backend: login or any authenticated call may return
  `403 { "error_code": "USE_PARTNER_APP", "message": "Salon partner accounts use the Lubist Partner app." }`
  (only when the backend's enforcement flag is on).
- App: the session is cleared and a full-screen **"Use the Lubist Partner app"**
  screen explains *"This is a salon partner account. Please use the Lubist
  Partner app."* with a button to
  `https://play.google.com/store/apps/details?id=com.lubist.partner` and a
  *Back to sign in* link.
- The existing client-side check on the email login screen (role `vendor` is
  never signed in) opens the same screen, so the experience is identical whether
  or not the backend flag is on. Other staff roles still get the web-portal alert.
- `AuthContext` still drops any stored `vendor` session on restore (`RETIRED_ROLES`).
- `403 USE_WEB_PORTAL` (account managed on the website) shows a variant pointing
  at `www.lubist.com`.

Screens should not show their own Alert for these errors; check
`isHandledGlobally(error)` from `services/api/client.ts` in `onError`.

## 5. Errors

Every failed call throws `ApiError` (`services/api/client.ts`) with
`status`, `code` (the backend's `error_code`, or null) and `message` (from
`message` / `detail` / `errors[]`). Existing `error.message` usage is unchanged.

## 6. Contract drift known at 2026-11-12

Endpoint audit: every path + method the app calls exists in the contract (62
hook calls, the token refresh, app-config). Type mismatches found while
migrating, and what was done:

| Where | Mismatch | Action |
|-------|----------|--------|
| `useCreateProductOrder` | sent `discount_total: 0`; `CreateOrderRequest` has no such field (server prices orders) | **Removed** |
| `CreateOrderRequest.coupon_code` | backend accepts a product coupon; the app never sends one | Left - product-coupon UI not built |
| `Salon.created_at` (list rows) | not in `SalonListResponse`, so the backend strips it; the Discover "New Arrivals" sort is a no-op | Left, overlaid + commented; needs `created_at` added to `SalonListResponse` |
| hand-written `Salon` | had `pincode`, `phone`, `email`, `has_discount` - none are returned on list rows | Removed (unused) |
| `SignInScreen` | `customer_name` can be `null` | Fixed (`?? undefined`) |
| signup screens | `gender` is required by `SignupRequest` | Fixed (guard; button was already disabled without it) |
| `CartItem` | contract also has `created_at`, `metadata` | Added to the optimistic cart line |
| `LoginResponse` | has no `message` field (hand-written type claimed one) | Now derived from contract |
| `/auth/me`, `/auth/signup/phone/verify-otp`, `/products/categories`, `/product-orders/create`, `/product-orders/verify`, `/location/reverse-geocode` | no response model in the contract | Hand-written types kept |
| `/product-orders/dev-verify/{id}` | exists, but returns 403 in production | Unchanged (dev-mode path only) |
